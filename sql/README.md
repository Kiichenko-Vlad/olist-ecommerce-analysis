## Загальні угоди

Усі 9 запитів дотримуються єдиних правил для забезпечення консистентності результатів.

**Визначення GMV:**
`GMV = SUM(price)` без урахування `freight_value` — тільки виручка від продажу товару. Використовується в Q2 і Q9.

**Фільтрація за статусом замовлення:**

| Запит      | Фільтр                                      | Причина                                                      |
| ---------- | ------------------------------------------- | ------------------------------------------------------------ |
| Q2, Q3, Q8 | `status = 'delivered'`                      | Метрики якості/доставки — тільки завершені                   |
| Q5, Q9     | `status NOT IN ('canceled', 'unavailable')` | Активність продавців і GMV — включаючи shipped               |
| Q1, Q4, Q6 | Без фільтру                                 | Повна активність платформи або відгуки незалежні від статусу |
| Q7         | Без фільтру                                 | Аналіз платежів охоплює всі транзакції                       |

**Ідентифікація клієнтів:**
У Q6 використовується `customer_unique_id`, а не `customer_id`. В Olist кожне замовлення отримує новий `customer_id` — тільки `customer_unique_id` дозволяє коректно відстежити повторні покупки.

**Ранжування:**
`DENSE_RANK()` замість `ROW_NUMBER()` — коректно обробляє можливі збіги значень між рядками.

**Час у днях:**
`EXTRACT(EPOCH FROM interval) / 86400` — PostgreSQL-специфічний підхід для конвертації інтервалу дат у дні.

## Аналітичні запити

### Q1 — Динаміка кількості замовлень по місяцях

**Файл:** `queries/q01_monthly_orders.sql`
**Бізнес-питання:** Яка динаміка замовлень по місяцях — чи росте платформа?

**Що повертає:** місяць у форматі `YYYY-MM` і кількість замовлень за цей місяць.

**SQL-техніки:** `DATE_TRUNC`, `TO_CHAR`, `GROUP BY`, `ORDER BY`.

**Результат (25 рядків):**

| Бакет           | Значення                                  |
| --------------- | ----------------------------------------- |
| Перший місяць   | 2016-09 (4 замовлення — неповні дані)     |
| Пік             | 2017-11: 7,544 замовлення (Black Friday)  |
| Плато 2018      | ~6,000–7,000 замовлень/місяць             |
| Останній місяць | 2018-10 (4 замовлення — обрізка датасету) |

**Ключовий висновок:** Платформа зросла з ~300 замовлень/місяць (початок 2017) до ~7,000 (2018) — приблизно у 20 разів за два роки. Дані по краях (вер–груд 2016 та вер–жовт 2018) неповні через обрізку датасету і не відображають реальну динаміку бізнесу.

**Ключовий висновок:** `watches_gifts` (R$1.17M) має найнижчу частку фрахту серед топ-10 (8.4%) — найкращий показник маржинальності. `furniture_decor` і `housewares` несуть найважче логістичне навантаження (~23%). Рекомендація: пріоритизувати залучення продавців у категорії з низьким freight_pct.

### Q3 — Середній час доставки по штатах з розбивкою за етапами

**Файл:** `queries/q03_delivery_time_by_state.sql`
**Бізнес-питання:** Який середній час доставки по штатах і де найгірша логістика?

**Що повертає:** рейтинг штату за часом доставки, код штату, кількість замовлень, середній час обробки продавцем (днів), середній транзит перевізника (днів), загальний середній час (днів), медіана, % запізнень.

**SQL-техніки:** CTE (2 рівні), `EXTRACT(EPOCH)/86400`, `PERCENTILE_CONT(0.5)`, `DENSE_RANK() OVER()`, JOIN двох таблиць.

**Результат (27 рядків — усі штати):**

| Штат            | avg_seller_handling | avg_carrier_transit | avg_total |
| --------------- | ------------------- | ------------------- | --------- |
| RR (найгірший)  | 3.74 дні            | 25.64 дні           | 29.39 дні |
| SP (найкращий)  | 3.16 дні            | 5.60 дні            | 8.76 дні  |
| Середнє по всіх | ~3–4 дні            | варіюється          | —         |

**Ключовий висновок:** Час обробки продавцем стабільно ~3–4 дні у всіх 27 штатах — затримки виключно на боці перевізника. Штати RR, AP, AM мають малі вибірки (41–80 замовлень) — результати слід інтерпретувати з обережністю.

### Q4 — Розподіл оцінок відгуків (1–5 зірок)

**Файл:** `queries/q04_review_score_distribution.sql`
**Бізнес-питання:** Як розподіляються оцінки відгуків і який % незадоволених клієнтів?

**Що повертає:** оцінка (1–5), кількість відгуків, частка від загального (%), накопичений відсоток (%).

**SQL-техніки:** вкладені віконні функції `SUM(COUNT(*)) OVER()` та `SUM(COUNT(*)) OVER(ORDER BY score)`, `GROUP BY`, `ROUND` з `::numeric` cast.

**Результат (5 рядків):**

| Score | Кількість | Частка | Накоп. % |
| ----- | --------- | ------ | -------- |
| 1     | 11,282    | 11.46% | 11.46%   |
| 2     | 3,114     | 3.16%  | 14.63%   |
| 3     | 8,097     | 8.23%  | 22.86%   |
| 4     | 19,007    | 19.31% | 42.17%   |
| 5     | 56,910    | 57.83% | 100%     |

**Ключовий висновок:** J-подібний розподіл — 57.83% оцінок 5, але 14.62% негативних (1–2). Оцінка 1 зустрічається у 3.6× частіше ніж 2 (11,282 vs 3,114): клієнти реагують на критичні збої, а не помірне незадоволення. Усунення причин score=1 — найшвидший важіль для покращення NPS.

### Q5 — Топ-10 продавців за обсягом замовлень з метриками якості

**Файл:** `queries/q05_top_sellers_quality.sql`
**Бізнес-питання:** Хто топ-10 продавців за активністю і яка їхня середня оцінка?

**Що повертає:** рейтинг, seller_id, місто, штат, кількість замовлень, середня оцінка, % критичних відгуків (1★), % негативних відгуків (1–2★).

**SQL-техніки:** CTE (3 рівні), `LEFT JOIN`, `COUNT(DISTINCT)`, `DENSE_RANK() OVER()`, `AVG` з `CASE WHEN` та `FILTER(WHERE IS NOT NULL)`.

**Результат (10 рядків):**

| Ранг | Місто     | Замовлень | avg_score | critical_pct |
| ---- | --------- | --------- | --------- | ------------ |
| 1    | sao paulo | 1,847     | 3.92      | 12.97%       |
| 7    | sao paulo | 1,159     | 4.23      | 7.74%        |
| 2    | ibitinga  | 1,804     | 3.81      | 14.73%       |

**Ключовий висновок:** Усі топ-10 продавців — зі штату SP. Кореляція між обсягом і якістю слабка: `critical_pct` варіюється від 7.74% до 14.73% — обсяг не гарантує якість. `FILTER(WHERE score IS NOT NULL)` критично важливий: без нього `LEFT JOIN` NULLs давали б 0 через `CASE WHEN` і занижували відсотки незадоволення.

### Q6 — Аналіз утримання клієнтів (Retention Analysis)

**Файл:** `queries/q06_customer_retention.sql`
**Бізнес-питання:** Яка частка клієнтів повертається для повторної покупки?

**Що повертає:** один підсумковий рядок — загальна кількість унікальних клієнтів, розбивка по сегментах воронки, `retention_pct` (%), `avg_orders_per_customer`, `max_orders_per_customer`.

**SQL-техніки:** CTE, `COUNT(*) FILTER (WHERE ...)`, `ROUND`, `AVG`, `MAX`.

**Результат (1 рядок):**

| total  | one_time | repeat (≥2) | frequent (≥3) | loyal (≥4) | power_users (≥5) | retention_pct | avg_orders | max_orders |
| ------ | -------- | ----------- | ------------- | ---------- | ---------------- | ------------- | ---------- | ---------- |
| 96,096 | 93,099   | 2,997       | 252           | 49         | 19               | 3.12%         | 1.03       | 17         |

**Ключовий висновок:** Retention rate — 3.12%. Середня кількість замовлень — 1.03 на клієнта. Платформа фактично залежить від постійного припливу нових клієнтів, а не від повторних покупок. Один клієнт зробив максимум 17 замовлень. Обрізка датасету (2016–2018) штучно занижує retention: клієнти з кінця 2018 не мали часу на другу покупку.

### Q7 — Розподіл способів оплати та середній чек

**Файл:** `queries/q07_payment_methods.sql`
**Бізнес-питання:** Який середній чек по кожному типу оплати?

**Що повертає:** тип оплати, кількість замовлень, частка від загального (%), середній чек (R$). Відсортовано за кількістю замовлень.

**SQL-техніки:** CTE, `SUM/COUNT/AVG` з `GROUP BY`, віконна функція `SUM(COUNT(*)) OVER()` для розрахунку частки.

**Результат (5 рядків):**

| ------------ | ------ | --------- | --------------- |

| boleto       | 19,784 | 19.46%    | R$145.03        |
| voucher      | 3,866  | 3.80%     | R$98.15         |
| debit_card   | 1,528  | 1.50%     | R$142.66        |

**Ключовий висновок:** `credit_card` домінує (75.24%) — зумовлено бразильським `parcelamento` (безвідсоткова розстрочка). `credit_card` і `boleto` відрізняються лише на 13% за середнім чеком (R$163.94 vs R$145.03) — це різні сегменти аудиторії з подібною купівельною спроможністю. `voucher` з низьким avg (R$98.15) використовується як доповнення до основного платежу.

### Q8 — Вплив часу доставки на оцінку відгуку клієнта

**Файл:** `queries/q08_delivery_time_vs_score.sql`
**Бізнес-питання:** Чи впливає час доставки на оцінку клієнта?

**Що повертає:** бакет часу доставки, кількість замовлень, середня оцінка відгуку.

**SQL-техніки:** CTE, `EXTRACT(EPOCH)/86400`, `CASE WHEN` для бакетування, `LEFT JOIN`, `ORDER BY MIN()` для коректного сортування рядкових бакетів.

**Результат (4 рядки):**

| Бакет        | Замовлень  | avg_score |
| ------------ | ---------- | --------- |
| 1–3 дні      | 8,582      | 4.46      |
| 4–7 днів     | 25,124     | 4.39      |
| 8–14 днів    | 36,517     | 4.29      |
| **15+ днів** | **26,484** | **3.65**  |

**Ключовий висновок:** Пороговий ефект на 15 днях: оцінка падає на -0.64 (4.29 → 3.65) — у 6× різкіше ніж між попередніми бакетами. 27.4% замовлень потрапляють у критичну зону 15+. Рекомендований SLA — 14 днів максимум. Статистичне підтвердження — у `04_analysis.ipynb` (t-test, p < 0.001, Cohen's d = 0.307).

## Крос-запитні висновки

Окремі запити утворюють зв'язану аналітичну картину:

**Логістика → задоволеність → виручка (Q3 + Q8 + Q9):**
Північні штати (RR, AP, AM) мають середній час доставки 26–29 днів (Q3) — майже всі їхні замовлення потрапляють у критичний бакет 15+ (Q8), де avg_score = 3.65. При цьому їхній середній чек на 37–73% вищий ніж у SP (Q9). Підвищення якості логістики в цих регіонах одночасно покращить оцінки і розблокує прихований GMV.

**Концентрація ризиків (Q5 + Q9):**
100% топ-10 продавців (Q5) і ~38% GMV (Q9) — зосереджені в одному штаті SP. Будь-який локальний збій б'є одночасно по пропозиції і попиту.

**Retention → зростання (Q1 + Q6):**
Платформа зросла у 20 разів за 2 роки (Q1), але retention — 3.12% (Q6). Плато 2018 тримається виключно на нових клієнтах: будь-яке сповільнення припливу безпосередньо б'є по GMV.
