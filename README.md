## Бізнес-проблема

Olist — бразильський маркетплейс, що з'єднує малих продавців з великими торговими майданчиками. Платформа активно зростала у 2016–2018, однак операційні проблеми не були видні зі стандартних дашбордів.

Проєкт відповідає на три ключових аналітичних питання:

1. **Що обмежує масштабування виручки:** географічна концентрація пропозиції чи логістичні бар'єри у регіонах із вищим середнім чеком?
2. **На якому пороговому значенні часу доставки** задоволеність клієнтів різко падає — і чия відповідальність: продавця чи перевізника?
3. **Які структурні причини утримують retention rate на рівні ~3%** і які зміни дадуть найбільший ефект?

## Якість даних

Первинне дослідження (EDA) виявило системні проблеми, вирішені на ETL-етапі:

| Проблема | Де | Рішення |
|---|---|---|
| Дати як рядки (тип `object`) | `orders` (5 кол.), `order_items` (1), `order_reviews` (2) | `pd.to_datetime()` |
| ~88% NULL у `comment_title`, ~59% у `comment_message` | `order_reviews` | Залишено як NULL — нормальна поведінка |
| ~0.01% NULL у вазі та розмірах товарів | `products` | Медіана по категорії |
| 814 рядків з дублікатами `review_id` | `order_reviews` | Дедуплікація по `(review_id, order_id)` |
| ~1,000,163 рядків на ~15k унікальних zip-кодів | `geolocation` | Медіана lat/lng на кожен zip |
| Відсутні англійські назви категорій | `products` | LEFT MERGE з таблицею перекладів |
| `delivered_at < purchased_at` (логічна помилка) | `orders` | Відфільтровано некоректні рядки |

Детальний ETL-процес — у [`notebooks/02_etl.ipynb`](notebooks/02_etl.ipynb).

## Аналітичні питання

| # | Питання | SQL-техніки |
|---|---|---|
| Q1 | Яка динаміка кількості замовлень по місяцях — чи росте платформа? | `DATE_TRUNC`, `GROUP BY` |
| Q2 | Які топ-10 категорій генерують найбільший дохід і яке логістичне навантаження? | CTE, `DENSE_RANK`, `JOIN` |
| Q3 | Який середній час доставки по штатах і де вузьке місце — продавець чи перевізник? | CTE, `EXTRACT(EPOCH)`, `PERCENTILE_CONT` |
| Q4 | Як розподіляються оцінки відгуків і який % незадоволених клієнтів? | Вкладені віконні функції `SUM(COUNT(*)) OVER()` |
| Q5 | Хто топ-10 продавців за активністю і яка їхня якість сервісу? | CTE, `LEFT JOIN`, `FILTER(WHERE IS NOT NULL)` |
| Q6 | Яка частка клієнтів повертається і наскільки глибокою є їхня лояльність? | `customer_unique_id`, `COUNT(*) FILTER` |
| Q7 | Як розподіляються способи оплати і який середній чек по кожному? | CTE, віконна функція частки |
| Q8 | На якому пороговому значенні часу доставки падає оцінка клієнта? | CTE, `CASE WHEN`, `ORDER BY MIN()` |
| Q9 | Яка географія доходів — які штати генерують найбільший GMV і де прихований потенціал? | `DENSE_RANK() OVER()`, `COUNT(DISTINCT)` |

## Ключові візуалізації

### Динаміка замовлень по місяцях (Q1)

![Orders by month](images/chart_01_orders_by_month.png)

Платформа зросла з ~300 до ~7,000 замовлень/місяць за 2 роки — ~20x. Листопад 2017 — підтверджений пік Black Friday. Дані по краях (вер–груд 2016, вер–жовт 2018) неповні через обрізку датасету.

### Вплив часу доставки на оцінку клієнта (Q8)

![Score vs delivery time](images/chart_05_score_vs_delivery_time.png)

Пороговий ефект: після 15 днів доставки середня оцінка обвалюється з 4.29 до 3.65 (-0.64 пункти) — у 6× різкіше ніж між попередніми бакетами. 27.4% замовлень потрапляють у критичний бакет 15+.

## Головні висновки

1. **Логістика — головне вузьке місце.** Затримки повністю на боці перевізника, не продавців: час оформлення продавцем стабільний ~3–4 дні у всіх 27 штатах. Транзит у північних штатах сягає 25.6 днів проти 5.6 у SP.

2. **Пороговий ефект 15 днів.** 27.4% замовлень перевищують поріг і отримують середню оцінку 3.65 замість 4.29+. Рекомендований SLA — максимум 14 днів для всіх маршрутів.

3. **Північ — ринок із прихованим потенціалом.** Avg order value у північних штатах на 37–73% вищий ніж у SP (R$171–216 vs R$126), але попит стримується логістичним бар'єром, а не відсутністю платоспроможності.

4. **Retention 3.12% — структурна вразливість.** Типовий клієнт приходить рівно один раз (avg 1.03 замовлення). Повторний клієнт генерує вдвічі більше виручки при тому самому CAC.

5. **SP-концентрація — операційний ризик.** ~38% GMV і 100% топ-10 продавців — з одного штату. Будь-який локальний збій б'є одночасно по постачанні і попиті.

6. **`watches_gifts` — найкращий ROI серед топ категорій.** Freight лише ~8.4% від виручки проти ~20% у `bed_bath_table` при порівнянному обсязі продажів.

7. **J-форма розподілу оцінок.** Одиниць у 3.6× більше ніж двійок (11,282 vs 3,114) — клієнти реагують на критичні збої, а не помірне незадоволення. Усунення причин score=1 — найшвидший важіль для покращення NPS.

## Статистичні гіпотези

| Гіпотеза | Тест | p-value | Висновок |
|---|---|---|---|
| Час доставки впливає на оцінку (поріг 7 днів) | t-test (`ttest_ind`) | < 0.001 | H₀ відхилено |
| Середній чек відрізняється за способом оплати | Kruskal-Wallis | < 0.001 | H₀ відхилено |

**Гіпотеза 1:** клієнти з доставкою ≤7 днів мають середню оцінку 4.413 проти 4.038 у групі >7 днів. Cohen's d = 0.307 — середній практичний ефект. Рекомендований SLA — 14 днів (критичний поріг падіння оцінки за даними Q8).

**Гіпотеза 2:** credit_card (R$163.94) і boleto (R$145.03) відрізняються лише на 13% — різні сегменти аудиторії з подібною купівельною спроможністю. Voucher (R$98.15) використовується як часткова оплата, а не самостійний метод.

## Як запустити

### 1. Клонувати репозиторій

```bash
git clone https://github.com/Kiichenko-Vlad/olist-ecommerce-analysis.git
cd olist-ecommerce-analysis
```

### 2. Встановити залежності

```bash
pip install -r requirements.txt
```

### 3. Налаштувати змінні середовища

```bash
cp .env.example .env
```

Відкрий `.env` і заповни параметри підключення:

```
DATABASE_URL=postgresql+psycopg2://postgres:your_password@localhost:5432/olist_db
```

### 4. Запустити PostgreSQL через Docker

```bash
docker run --name olist_db \
  -e POSTGRES_PASSWORD=your_password \
  -p 5432:5432 \
  -d postgres:16
```

### 5. Створити схему бази даних

```bash
psql -U postgres -d olist_db -f sql/create_tables.sql
```

### 6. Завантажити датасет

Завантаж [Brazilian E-Commerce Public Dataset](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) з Kaggle і розпакуй CSV-файли в `data/raw/`.

### 7. Запустити ETL-пайплайн

```bash
python main.py
```

Після виконання у консолі відобразиться верифікація: `COUNT(*)` у БД має збігатись з кількістю рядків після трансформацій.

### 8. Відкрити ноутбуки

```bash
jupyter notebook
```

Відкривай ноутбуки в папці `notebooks/` у порядку нумерації: `00_intro` → `01_eda` → `02_etl` → `03_visualizations` → `04_analysis` → `05_conclusions`.
